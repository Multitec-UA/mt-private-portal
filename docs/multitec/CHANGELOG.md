# Multitec changelog

Everything Multitec changes in this fork, newest first. Upstream's `CHANGELOG.md` is
generated by semantic-release and is not ours to touch.

Each entry says **what changed, why, and the evidence it works** — the command that was
run and what it printed. "It should work" is not an entry.

An upstream sync is a change too: record which release came in, what conflicted, and what
was verified afterwards.

---

## 2026-08-28 — fork taken, working rules established

**What.** Forked `homarr-labs/homarr` into `Multitec-UA/mt-private-portal` at
`upstream/dev` `331925c19` (release `v1.76.2`). Created the `multitec` branch and added,
all in our own namespace so upstream can never collide with it:

- `MULTITEC.md` — the fork constitution: additive-first, no deletions of upstream files,
  no reformatting, our own env/doc/skill namespaces, every feature off by default.
- `CLAUDE.md` — a pointer to `MULTITEC.md` and upstream's `AGENTS.md`.
- `docs/multitec/architecture-notes.md` — what reading the codebase actually taught us,
  with file:line references: the container runs cron and the WebSocket server *inside* the
  Next.js process; media is a database blob, not a file; the provider list is data; group
  sync is already provider-agnostic; `users.provider` is plain text, so a new auth provider
  needs no migration.
- `docs/multitec/UPSTREAM-TOUCHPOINTS.md` — the registry of every upstream file we modify.
  Currently **empty**, which is the ideal state.
- `docs/multitec/upstream-sync.md` — the merge procedure, including the two conflicts that
  will actually happen (`pnpm-lock.yaml`, the registered auth files).
- `docs/multitec/adr/0001-fork-strategy.md`, `docs/multitec/adr/0002-iap-authentication.md`.
- `docs/multitec/tools/upstream-guard.sh` + its self-test.
- `.agents/skills/multitec-upstream-sync/`, `.agents/skills/multitec-portal-work/`.

**Why.** Homarr releases roughly weekly. A fork that cannot follow upstream stops getting
security fixes and turns into a rewrite. Every rule above exists to keep the merge cheap,
and the guard exists because rules that do not fail a build decay.

**Evidence.**

```
$ docs/multitec/tools/test-upstream-guard.sh
… 14 PASS, 0 FAIL
RESULT: all pass

$ docs/multitec/tools/upstream-guard.sh
upstream-guard: comparing HEAD against upstream/dev (merge-base 331925c19)
upstream-guard: OK — 0 upstream file(s) touched, all registered (budget 12)
```

**Not done, deliberately.** No application code changed. The IAP provider in ADR 0002 is a
design, not an implementation, and it does not start until the phase-0 spike answers
whether Homarr's WebSockets survive IAP.
